# ChatTask クリーンルーム再構築仕様書

## 1. 文書情報

- 文書種別: 個人利用向けタスク管理アプリの再構築仕様
- 想定用途: 私有PC上で、既存ソースコードや業務データを持ち出さずに新規実装するための参照資料
- 作成日: 2026-08-27
- 対象プラットフォーム: デスクトップ（macOSを主対象とし、可能ならWindowsにも対応）
- データ保存方針: 端末内へのローカル保存

### 1.1 この文書に含めないもの

本書は機能と振る舞いのみを記述し、次の情報を含めない。

- 実際のタスク、案件、顧客、担当者、社内用語
- 実データベース、バックアップ、添付ファイル
- 既存アプリのソースコード
- 既存画面の画像、ロゴ、固有デザイン素材
- APIキー、認証情報、接続情報
- 会社固有の業務フローや機密情報

> 注意: 本書自体の社外持ち出し可否は、所属組織の規程に従って利用者自身が確認すること。以下は一般的な個人用タスク管理アプリの仕様として記述している。

---

## 2. 目的

利用者本人が、単発タスク、複数日にわたる作業、確認待ち、定期作業および小規模プロジェクトを一つのローカルアプリで管理できるようにする。

特に、次の二つを分離して管理できることを重視する。

- 期限: いつまでに完了すべきか
- 作業予定: いつ実行するか

本アプリは個人利用を前提とし、チーム共同編集、承認フロー、クラウド同期は必須要件としない。

---

## 3. 設計原則

1. データは端末内に保存し、明示的な操作なしに外部送信しない。
2. タスク作成時の必須入力はタイトルだけとする。
3. 高度な機能は必要な場合だけ使用できるようにする。
4. 期限と作業予定を別の情報として保持する。
5. タスクの削除やデータ復元など、損失を伴う操作には確認を設ける。
6. 保存形式にはバージョン番号を持たせ、将来の移行に備える。
7. 最初から全機能を作らず、MVPから段階的に実装できる構造にする。

- 予定工数、実績工数
- 非稼働日
- Inbox
- タスクテンプレート
- 高度な検索条件と保存ビュー

### 4.3 任意の拡張

| 用語 | 意味 |

## 6. 画面構成

### 6.1 メイン画面

```text
┌───────────────────────────────────────────────────────┐
│ アプリ名     検索                       今日  設定      │
├─────────────────┬─────────────────────────────────────┤
│ フィルター       │ 選択したタスクの詳細                 │
│ 案件タグ         │                                     │
│                 │ タイトル・状態・優先度               │
│ タスク一覧       │ 期限・予定・メモ・関連情報           │
│                 │                                     │
└─────────────────┴─────────────────────────────────────┘
```

- 左側にフィルター、案件タグ、タスク一覧を表示する。
- 右側に選択中タスクの詳細を表示する。
- 狭い画面では、一覧と詳細を一画面ずつ表示してもよい。
- 最後に選択したタスクや表示設定は、次回起動時に復元してよい。

### 6.2 今日の画面

指定日の行動を決める画面とする。最低限、次の区分を表示する。

- その日の作業予定
- その日に確認すべき待ちタスク
- 期限が到来または超過したタスク
- 定期タスク
- 未完了の持ち越し候補
- その日の日次メモ

### 6.3 補助画面

- タスク新規作成
- タグ設定
- 定期設定
- 待ち情報
- 検索・高度な絞り込み
- データ管理
- 非稼働日設定
- プロジェクト管理（任意）
- ドキュメント管理（任意）
- ガントチャート（任意）

## 7. タスク仕様

### 7.1 基本項目

| 項目 | 必須 | 仕様 |
| --- | --- | --- |
| ID | 必須 | UUIDなどの重複しない値 |
| タイトル | 必須 | 空白だけの登録は禁止 |
| 説明 | 任意 | 複数行テキスト |
| 優先度 | 必須 | A、B、C、D。初期値はB |
| 進捗状態 | 必須 | 未着手、進行中、待ち、完了 |
| 待ち理由 | 必須 | なし、相手、チーム、レビュー、その他 |
| 種別 | 必須 | 通常、定期 |
| 案件タグ | 任意 | 一つのタグを選択 |
| 親タスク | 任意 | 自分自身および子孫は指定不可 |
| 次のアクション | 任意 | 次に行う具体的行動 |
| 期限 | 任意 | `YYYY-MM-DD` |
| リマインド日 | 任意 | `YYYY-MM-DD` |
| 作成日時 | 必須 | ISO 8601 |
| 更新日時 | 必須 | ISO 8601 |
| 完了日時 | 任意 | 完了時に記録 |

### 7.2 状態

内部的には、次の三軸へ分離する。

```text
進捗状態: 未着手 / 進行中 / 待ち / 完了
待ち理由: なし / 相手 / チーム / レビュー / その他
タスク種別: 通常 / 定期
```

画面上では、利用者が分かりやすいように次の表示状態へまとめてもよい。

- 未対応
- 進行中
- 待ち
- 先方確認待ち
- チーム確認待ち
- レビュー待ち
- 保留
- 定期
- 完了
- 中止
- 引き継ぎ済み

終了状態は「完了」「中止」「引き継ぎ済み」とする。終了状態へ変更した場合は完了日時を記録し、終了状態を解除した場合は完了日時を消去する。

### 7.3 優先度

- A: 最優先
- B: 通常
- C: 低め
- D: 参考または余裕があるとき

色だけに依存せず、必ず文字でも優先度を表示する。

### 7.4 親子関係

- 一つのタスクは最大一つの親タスクを持てる。
- 親タスクには複数の子タスクを設定できる。
- 自分自身を親にできない。
- 循環参照を禁止する。
- 親の完了と子の完了は自動連動させない。
- 親には子タスクの完了数を表示してよい。

### 7.5 関連タスク

親子関係とは別に、次の関連を設定できる。

- 参照
- 前工程
- 引き継ぎ

削除されたタスクへの参照は、整合性チェックで検出する。

## 8. 期限と作業予定

### 8.1 基本ルール

- 期限はタスク全体に一つ設定できる。
- 作業予定は一つのタスクに複数設定できる。
- 作業予定には開始日と終了日を設定する。
- 同じ日に複数の作業予定を登録できる。
- 開始日は終了日以前でなければならない。
- 期限と作業予定は自動的に同じ値へ同期しない。

### 8.2 作業予定の項目

| 項目 | 仕様 |
| --- | --- |
| ID | タスク内で一意 |
| 開始日・終了日 | 必須 |
| タイトル | 任意 |
| 説明・メモ | 任意 |
| 予定工数 | 0以上の数値 |
| 状態 | 未着手、進行中、完了 |
| 表示順 | 同一開始日の並び順 |
| 連携元 | 任意。マイルストーンまたは作業項目 |

### 8.3 日別計画

- 作業予定の対象日ごとに具体的な実施内容を入力できる。
- 日単位で達成状態を記録できる。
- 日単位で実績工数を記録できる。
- 同日に複数予定がある場合は、日付と予定IDの組み合わせで識別する。

### 8.4 持ち越し

- 未完了の作業予定を別日へ持ち越せる。
- 元の日、移動先、元予定IDを履歴として保持する。
- 同じ元予定に対する重複持ち越しを避ける。
- 元の日に実績がある場合も、実績値は元の日に残す。

### 8.5 前倒し

- 将来の作業予定をより早い日へ移せる。
- 元の期間、理由、実行日時を記録する。

---

## 9. 待ちタスク

待ち状態では、任意で次を記録する。

| 項目 | 内容 |
| --- | --- |
| 待ち種別 | GO、確認、返信、資料、作業、その他 |
| 相手 | 待ちの対象。自由入力 |
| 開始日 | 待ち始めた日 |
| 確認日 | 次回確認する日 |
| メモ | 状況や次の対応 |
| 最終確認日 | 最後に確認した日 |

- 待ち状態を解除すると、その時点の内容を待ち履歴へ移す。
- 確認日が今日以前のものを「今日の待ち」に表示する。
- 個人情報や業務上の機密を入力するかどうかは、利用環境のルールに従う。

## 10. 定期タスク

### 10.1 設定

- 周期: 毎日、毎週、毎月
- 毎週: 曜日を指定
- 毎月: 日付、または第N曜日を指定
- 開始日
- 終了日（任意）
- 一時停止
- 実施時に使用するメモのひな型

### 10.2 実施記録

対象日ごとに次のいずれかを記録する。

- 未処理
- 実施済み
- スキップ
- 別日へ移動

別日へ移動する場合は、移動先、理由、記録日時を保持する。定期タスク本体を完了扱いにせず、各回の記録を独立して管理する。

## 11. タグ

- タグの追加、名称変更、表示・非表示、並び替え、削除ができる。
- タグは名称、色、任意のアイコンを持てる。
- タグ削除時は、関連タスクを削除せずタグ割り当てだけ解除する。
- タグ単位で共通リンクや共通ドキュメントを保持してもよい。

### 12.1 基本フィルター

- 未完了
- すべて
- 今日やる
- 今日確認する待ち
- 進行中
- 待ち
- 期限またはリマインドあり
- 終了済み

### 12.2 検索対象

- タスクタイトル
- 説明
- 次のアクション
- コメントと履歴
- タグ名
- リンク名とURL
- ドキュメント名と本文

### 12.3 絞り込み

- 状態
- 優先度
- タグ
- 今日の対象か
- 期限の有無または範囲
- テキスト

複数条件はANDまたはORで結合できる。よく使う条件は名前を付けて保存できる。

### 12.4 並び替え

- 今日の対象
- 優先度
- 期限
- 更新日時
- 作成日時
- タイトル

複数の並び替え規則を上から順に適用できる。

## 13. Inbox

- 思いついた内容を、詳細設定なしで一時保存する。
- 項目はタイトル、本文、タグ、確認日を持つ。
- Inbox、処理済み、タスク化済みの状態を持つ。
- タスク化するときにタイトル、説明、次のアクション、タグ、優先度、状態、親タスクを確認する。
- 元のInbox項目から作成したタスクへ移動できる。

---

## 14. コメントと活動履歴

### 14.1 コメント

- タスクに時系列のメモを追加できる。
- コメントは編集・削除できる。
- 作成日時と、編集した場合は編集日時を記録する。
- Markdownの簡易表示に対応してよい。

### 14.2 システム履歴

最低限、次の操作を記録する。

- タスク作成、削除
- 状態変更、完了解除
- 作業予定の追加、変更、持ち越し
- 定期タスクの実施、スキップ、移動
- コメント追加

履歴にはイベントID、対象タスクID、概要、詳細、発生日時を保持する。

## 15. プロジェクト管理（任意）

### 15.1 プロジェクト

プロジェクトは次の情報を持つ。

- 名称、説明
- 達成条件（GOAL）
- GOAL期限
- 状態
- 優先度
- 案件タグ
- 起点タスク、関連タスク
- マイルストーン
- 作業項目
- 振り返り
- 共通リンク、共通ドキュメント

状態は、未着手、進行中、一時停止、達成、アーカイブ、中止とする。

### 15.2 マイルストーン

- 中間的な達成状態を表す。
- 名称、説明、期限、状態、予定期間、予定工数を持つ。
- 必要な場合だけ通常タスクへ関連付ける。
- 表示順を変更できる。

### 15.3 作業項目

- マイルストーン達成のための具体的行動を表す。
- 名称、説明、状態、優先度、期限、予定・実績工数、予定期間を持つ。
- 必要な場合だけ通常タスクへ関連付ける。

### 15.4 基準計画と再計画

- 初期の予定期間と予定工数を基準計画として保存できる。
- 計画変更時は変更理由と変更日時を記録する。
- 現在計画と基準計画を比較できる。

---

## 16. ドキュメントと添付（任意）

### 16.1 ドキュメント

- タスク、タグ、プロジェクトに複数のMarkdown文書を保持できる。
- 文書とフォルダを同一ツリー内で管理する。
- 親フォルダはID参照で表現し、循環を禁止する。
- 文書はタイトル、本文、種類、親ID、表示順、作成・更新日時を持つ。
- 編集、プレビュー、左右分割表示を選択できる。
- Markdownから生成したHTMLは必ずサニタイズする。

### 16.2 添付ファイル

- 添付メタデータとファイル本体を分離して保存する。
- ファイル本体はアプリデータ領域内へランダムな保存名で格納する。
- 元ファイル名、MIMEタイプ、サイズ、作成日時をメタデータとして保持する。
- 添付を開く、名前変更、保存先を指定して書き出す、削除する操作を提供する。
- 外部パスを無検証で連結せず、パストラバーサルを防止する。

## 17. データモデル概要

実装言語に依存しない論理モデルを以下に示す。

```text
AppData
├─ version
├─ tasks[]
│  ├─ basic fields
│  ├─ plannedRanges[]
│  ├─ recurrence + recurrenceRecords[]
│  ├─ dailyPlans{}
│  ├─ dailyCompletion{}
│  ├─ dailyActualHours{}
│  ├─ links[] + relatedTasks[]
│  ├─ documents[]
│  └─ history[]
├─ projectTags[]
├─ activityLog[]
├─ dailyNotes{}
├─ nonWorkingPeriods[]
├─ projects[]
├─ inboxItems[]
└─ settings
```

### 17.1 IDと日時

- IDはUUID v4など、端末内で衝突しにくい形式を使用する。
- 日付だけの値は`YYYY-MM-DD`で保存する。
- 時刻を含む値はISO 8601で保存する。
- 表示時に利用者のローカルタイムゾーンへ変換する。

### 17.2 参照整合性

次を検査できるようにする。

- 重複ID
- 存在しない親タスク、タグ、関連タスクへの参照
- 親子関係やフォルダ関係の循環
- 開始日より前の終了日
- 負数または数値でない工数
- 終了状態と完了日時の不一致
- 存在しないマイルストーンや作業項目への参照

## 18. ローカル保存

### 18.1 保存先

- OSが提供するアプリ専用データディレクトリを使用する。
- ソースコードのディレクトリやGitリポジトリ内へ実データを保存しない。
- 本番データとテストデータは別のDBファイルへ保存する。

推奨ファイル構成:

```text
app-data-directory/
├─ app-data.sqlite3
├─ app-data-test.sqlite3
├─ attachments.sqlite3
├─ attachments/
├─ profile/
└─ backups/
   ├─ production/
   └─ test/
```

### 18.2 SQLite

最低限、次の単位でテーブルを分ける。

- tasks
- task_history
- task_planned_ranges
- task_recurrence_records
- task_daily_plans
- task_documents
- project_tags
- projects
- project_milestones
- project_work_items
- activity_log
- daily_notes
- non_working_periods
- inbox_itemsまたは汎用settings
- app_meta
- schema_migrations

- 外部キーを有効にする。
- 複数テーブルの更新はトランザクション内で行う。
- DBスキーマの変更履歴をバージョン管理する。
- 書き込み失敗時に画面上でエラーを通知する。

### 18.3 Git除外

少なくとも次を`.gitignore`へ追加する。

```gitignore
*.db
*.db-journal
*.db-wal
*.db-shm
*.sqlite
*.sqlite-journal
*.sqlite-wal
*.sqlite-shm
*.sqlite3
*.sqlite3-journal
*.sqlite3-wal
*.sqlite3-shm
app-data/
runtime-data/
backups/
attachments/
```

コミット前に、追跡対象へDB、JSON出力、添付、ログが含まれていないことを確認する。

## 19. バックアップ、復元、移行

### 19.1 バックアップ

- 利用者が手動でJSONバックアップを作成できる。
- 一定間隔で自動バックアップを作成してよい。
- バックアップには形式バージョン、作成日時、アプリデータを含める。
- 添付ファイルをJSONへ含めるかどうかは明示する。初期実装では含めなくてもよい。
- 保存世代数または保存期間を設定し、無制限に増えないようにする。

### 19.2 復元

1. バックアップのJSON構文を検証する。
2. 必須項目と形式バージョンを検証する。
3. 現在データの退避バックアップを作成する。
4. トランザクション内で復元する。
5. 整合性チェックを実行する。
6. 成功後に画面データを再読込する。

### 19.3 外部持ち出し時の原則

- 実データのJSONエクスポートを、再構築用資料として使用しない。
- 再構築確認には架空のサンプルデータを新規作成する。
- 実タスク名、コメント、URL、添付ファイルをコピーしない。
- 既存DBやアプリデータディレクトリを私有PCへコピーしない。

---

## 20. セキュリティとプライバシー

- ネットワーク通信は初期状態で行わない。
- テレメトリー、クラッシュ送信、自動同期は初期状態で無効とする。
- 外部リンクはOSの既定ブラウザで開き、実行可能なURLスキームを制限する。
- MarkdownのHTMLはサニタイズする。
- 添付ファイル名を保存パスとして直接使用しない。
- エラーログへタスク本文や添付内容を出力しない。
- バックアップには機微情報が含まれ得ることを画面上で通知する。
- 必要ならOSのディスク暗号化を利用する。
- AI機能、クラウドAPI、外部分析SDKは必須要件に含めない。

---

## 21. 非機能要件

### 21.1 操作性

- 一般的なタスク追加は数秒で完了できる。
- 保存処理中と保存失敗を識別できる。
- キーボード操作を妨げない。
- 色だけに依存せず、文字やアイコンを併用する。

### 21.2 性能

- 数千件程度のタスクを想定する。
- 一覧の絞り込みや検索は、通常利用で即座に反応することを目標とする。
- 大きな添付ファイルをアプリ状態へ直接読み込んだまま保持しない。

### 21.3 信頼性

- アプリ終了直前の変更が失われない。
- 保存は直列化し、古い状態が新しい状態を上書きしない。
- DB更新は可能な限りトランザクション化する。
- 起動時に読込不能な場合、DBを上書きせずエラーを表示する。

### 21.4 保守性

- UI、ドメインロジック、永続化処理を分離する。
- データの正規化と移行処理を一箇所へ集約する。
- 重要な日付計算と状態遷移には自動テストを用意する。

---

## 22. 推奨技術構成（変更可）

本仕様は技術を固定しない。デスクトップアプリとして再構築する場合の一例を示す。

- UI: React + TypeScript
- ビルド: Vite
- デスクトップコンテナ: Tauri
- ローカルDB: SQLite
- Markdown: CommonMark/GFM対応パーサー
- HTMLサニタイズ: 実績のあるサニタイズライブラリ
- ID: UUID
- テスト: TypeScriptの単体テストとRust側のDBテスト

依存パッケージは必要最小限にし、固定バージョンとロックファイルを使用する。

## 23. 実装順序

### フェーズ1: 土台

1. 空のデスクトップアプリを作成する。
2. SQLite接続とマイグレーションを実装する。
3. タスクの作成、編集、完了、削除を実装する。
4. タグ、優先度、状態を実装する。
5. JSONバックアップと復元を実装する。

### フェーズ2: 「いつするか」の管理

1. 期限と作業予定を分離する。
2. 複数の作業予定を実装する。
3. 今日の画面を実装する。
4. 日別計画と持ち越しを実装する。
5. 定期タスクと待ち確認日を実装する。

### フェーズ3: 整理と記録

1. 検索、フィルター、並び替えを実装する。
2. コメント、履歴、Inboxを実装する。
3. 工数、非稼働日、レポートを実装する。

### フェーズ4: 任意拡張

1. プロジェクトとマイルストーンを実装する。
2. ドキュメントと添付を実装する。
3. ガントチャートと集計を実装する。

各フェーズの完了時に架空データでバックアップと復元を検証する。

## 24. MVP受入条件

- [ ] タイトルだけでタスクを作成できる。
- [ ] タスクを編集、完了、完了解除、削除できる。
- [ ] 状態と優先度で一覧を絞り込める。
- [ ] タグを作成し、タスクへ設定できる。
- [ ] 期限と作業予定を別々に設定できる。
- [ ] 一つのタスクへ複数の作業予定を設定できる。
- [ ] 今日の作業予定と期限超過を確認できる。
- [ ] 待ちタスクの次回確認日を確認できる。
- [ ] 定期タスクの各回を実施済みまたはスキップにできる。
- [ ] コメントを時系列で追加できる。
- [ ] アプリを再起動してもデータが残る。
- [ ] JSONバックアップを作成できる。
- [ ] 復元前に現在データが自動退避される。
- [ ] 不正なバックアップを読み込んでも現在データが壊れない。
- [ ] DB、バックアップ、添付がGitの追跡対象にならない。
- [ ] 通常利用で外部ネットワーク通信が発生しない。

## 25. 再構築時に意図的に変更してよい点

クリーンルーム再構築では、既存アプリとの画面・内部構造の完全一致を求めない。次を変更してよい。

- 画面レイアウト、色、余白、アイコン
- コンポーネント名、ファイル名、DBテーブル名
- 内部状態の表現方法
- 使用するフレームワークやライブラリ
- 任意機能の削除または実装順序
- 状態名やタグ名など、個人利用に適した用語

維持すべき中心概念は、「期限」と「作業予定」の分離、「今日の行動」の可視化、「待ちの再確認」、「ローカル保存」の四点とする。
